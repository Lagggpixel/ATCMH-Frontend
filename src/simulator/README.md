# ATCMH ATC Trainer

An EGPH training simulator with persistent, server-backed sessions. `/simulator/staff` opens the session library; `/simulator/mentee` accepts a unique mentee link or full session ID. Both use the existing website sign-in and require an authorized Dashboard staff role (moderator or mentor), Admin, superadmin, or Simulator Tester membership. This applies to both training seats, codes/links, assignments and all session/scenario APIs. A link or assignment alone does not grant access; learners without a staff/admin role need Simulator Tester membership. All authorized simulator users share the staff scenarios, sessions and assignments workspace. Creator names are shown, with immutable account IDs as a fallback. Existing learner assignment and seat restrictions still apply. Public about, attribution and source-download pages remain readable.

## Pilot requests and controller replies

Staff select a request under **Pilot messages**, choose its runway/direction when offered, then press **Send request** (**Send again** after the same transmission). Controller choices below are on the mentee's **Commands** menu. **Readback** acknowledges a movement command; **Readback & assign** also executes it. With **Automatic** enabled, the server does both after 1.5 exercise seconds. A request does not itself grant clearance. **Go Around** is an announcement and starts the pilot's manoeuvre immediately, including with automation off.

The examples use callsign `Easy 201`, runway `24`, direction `north` and published information `BRAVO`. Other runway/direction choices use the same templates.

Pushback/taxi requests read the latest **published** ATIS at execution, including scheduled scenario requests. Draft ATIS edits do not change the reported information. Until an ATIS is published, the request omits the information suffix and the staff UI explains why. Legacy scenario request identifiers/labels remain readable; new scenario events can store a departure direction and taxi runway preference.

New structured **Request Landing** and **Request the Option** transmissions create a mentor-only **Expected replies** checklist: **Pattern Entry → Sequence when not first → Landing/Option Clearance**. It observes transmitted commands in that order on the requested runway, supports entry with combined sequencing, and ignores withdrawn/Unable responses. A new request resets progress; a new circuit expires it. This is an instructor observation aid, not automatic grading or a movement restriction. The trainee sees the pilot transmission and the normal command menu, with no checklist, suggested next command, reordered buttons or workflow-based validation errors. A premature clearance remains possible for the mentor to assess; it does not complete the checklist. Sequencing is based on current traffic for the requested runway. Request identity and circuit are saved with the radio history; no expected-answer list is sent in shared snapshots.

Five unanswered pilot requests have a lime-text shortcut as the first mentee command: **Request Pushback → Pushback Approved**, **Request Runway Change → Unable**, **Request runway crossing → Cross Runway**, **Go Around → Go Around**, and **Request Transition → Approve transition**. The shortcut duplicates the ordinary command and opens the same submenu or sends the same instruction. Every original button stays in its relative position, shifted down by one. Approve transition shares the Respond to Transition altitude menu: 500–10,000 feet in 500-foot steps. The ordinary **Unable** command is available only while a runway-change request is pending; the generic Unable button above every request has been removed. Landing and option have no shortcut. Standby preserves the pending shortcut; an answer removes it. Older radio-only requests and automatic self-go-around announcements are recognized as well.

Staff global/aircraft and mentee general/aircraft message logs open at the latest message and follow new transmissions while at the bottom. Scrolling up with a wheel, keyboard, touch or scrollbar suspends following for that log, preserving the visible message as older history is trimmed. Returning to the bottom resumes following. Each log scrolls independently; new aircraft messages do not scroll the mentee's command menu.

Landing and option permissions last one circuit. Touchdown, a go-around, circuit wrap, runway reassignment or **Cancel Landing Clearance** removes the permission. A delayed landing command from an earlier circuit cannot be assigned. **Cleared to Land** requires a full stop, even if the aircraft's requested outcome was touch-and-go. **Cleared for the Option** permits the selected full-stop/touch-and-go outcome for this circuit only. A runway-heading go-around climbs straight ahead until another manoeuvre is assigned; left/right replies resume the selected circuit after climbing.

With automation on, crossing the final threshold without either permission starts a go-around and sends `Easy 201, going around` once through the normal unread/log/audio pipeline. With automation off, the aircraft continues its current action without a generated announcement. Movement prediction uses the same choice but cannot transmit radio messages. **Frequency Change Approved** releases the aircraft silently: it has no pilot readback; manual staff can use **Assign frequency release**. Contact instructions alone produce the `Contacting …` reply.

## Setup and sessions

Controller radio messages include Say Intentions, Standby, Correction, Standby and Disregard last message. They do not assign movement or fabricate automatic pilot replies; staff can supply intentions through Other pilot response. Correction, Standby withdraws the latest pending instruction, while Disregard withdraws the immediately preceding controller transmission to that aircraft on the selected channel. Withdrawal cancels queued assignment/readback and preserves already completed movement. The mentee's Unable command rejects a pending runway-change request. Staff can still send a pilot Unable reply rejecting a clearance. Hold-short choices show both runway ends (24 and 06 at EGPH).

Set `SIMULATOR_ENABLED=true` in the frontend environment and retain the normal central authentication, CSRF and `MYSQL_*` configuration. The feature is disabled by default. Apply `migrations/2026-10-10-simulator-sessions.sql` to the existing `atcmh_lms` database before enabling this release. The frontend database account needs SELECT, INSERT, UPDATE and DELETE on `simulator_sessions`; the migration does not change existing tables. The simulator engine runs in the frontend service. The legal-risk remediation also changes backend consent metadata; release both policy documents and the matching registry together.

Start a named session in the library and share its unique mentee URL. Staff and mentee can use different signed-in accounts, browsers and devices on the same deployed origin. The full UUID in the URL identifies the session; the short EGPH code is a display label. Any authorized simulator user with an unassigned mentee link can claim its mentee seat. Any authorized simulator user can claim a free staff seat or end a session. Another staff member cannot end, finish or restart it while its control seat is occupied.

Each session permits one control page and one mentee page. Atomic database row locks prevent competing seat claims across processes. A second page receives an explicit occupied-seat error. Closing a page releases its seat; a crashed or disconnected page releases it after the 15-second lease expires. Reconnection renews the same page token. Closing all pages keeps the session until the inactivity retention period. Continue restores the saved scenario; **End session** removes the live snapshot and invalidates its link, while saved attempt history remains. Reset affects only the selected scenario. An optional import creates an editable scenario from the older browser exercise; publish it before creating a session.

The server validates and orders commands, deduplicates retries, advances the deterministic engine and saves snapshots transactionally. Both roles receive streamed updates every 200 ms and render smooth motion between authoritative frames. Staff disconnection does not pause the exercise while a mentee remains connected. With all pages closed, the saved exercise resumes without replaying offline time. Only an explicit staff Pause hides the mentee’s entire display behind the gray pause screen. Streams recheck authentication every minute.

For local development, run `npm run dev` against the configured remote development services. No persistent local database or Docker application container is required. The session API is under `/api/simulator/sessions`; mutations use the existing central-session CSRF token.

Account-persistent automation requires `migrations/2026-10-10-simulator-staff-preferences.sql` after the sessions/scenarios migrations and before deployment. It adds `simulator_staff_preferences`, keyed by the central staff account; the frontend database account needs SELECT, INSERT and UPDATE on this table. Back up the live schema before applying it. This migration was applied on 2026-10-11. Preference writes and exercise updates commit atomically through the existing authenticated command endpoint. Ending sessions does not delete the account preference.

Apply `migrations/2026-10-11-simulator-shared-workspace.sql` and then `migrations/2026-10-11-simulator-creator-labels.sql` before frontend 1.8.50. It adds nullable creator-name snapshots to sessions, scenarios and assignments, backfills names from existing Discord identities (or the same account's active IFC identity when its Discord name is missing), and adds indexes for the shared lists. Existing IDs, content, revisions, attempts and seat snapshots are preserved. Back up the simulator tables privately before applying it. The application continues to use its existing database permissions; no grants are changed. Staff automation preferences remain personal.

## Scenarios and assignments

Apply `migrations/2026-10-10-simulator-scenarios.sql` **after** the sessions migration and **before** deploying the authoring UI. It adds a nullable private runtime column to `simulator_sessions` and four InnoDB tables: `simulator_scenarios`, `simulator_scenario_revisions`, `simulator_assignments` and `simulator_attempts`. Back up the affected live schema/session table before an authorized migration. The frontend account needs SELECT, INSERT and UPDATE on the new tables in addition to its existing session permissions. No backend changes or background worker are required. The production migration and frontend 1.8.46 release were verified on 2026-10-10; see the project AGENTS.md release record before applying this to another environment.

Staff reach **Scenarios** and **Assignments** from the simulator session library. `/simulator/scenarios/new` opens the unified-scope editor; `/simulator/assignments` assigns published scenarios. `/simulator/mentee/assignments` shows only assignments for the signed-in account. Authoring, publishing, assignment creation and attempt management require authorized simulator access and are shared across the staff workspace. Mentee assignment reads remain restricted to that learner. Creator attribution is never reassigned by edits, publication or staff handoff. All mutations retain the existing origin and CSRF checks.

The editor supports initial and scheduled traffic, mapped parking stands, map placement, runway thresholds, A* or manually drawn taxi routes, hold points and separate display-only flight plans. Inspect the stand endpoint and aircraft heading before publishing: the OSM parking centerlines do not identify the parked nose. **Save as scenario** on a live control page captures positions/settings without messages, unread counts or trails. It creates an independent draft, leaving the live exercise unchanged.

Events can run at an exercise time, after a latched condition and delay, or on instructor release. Conditions include reaching a hold point/location, tuning a frequency, entering a pattern leg and completing another event. Actions include spawning/removing traffic, sending a catalog pilot request/custom transmission, applying a staff manoeuvre and displaying a private instructor note. An event's ordered actions commit together; an invalid action blocks the entire event with a visible reason. Staff may retry or skip it. Same-time events follow the authored list order. Requests arrive unread through the existing radio/log pipeline; Go Around starts its announced manoeuvre, while other requests do not execute aircraft instructions; staff still choose Readback, Readback & assign or Unable.

**Test** rehearses the current draft locally without database writes. **Publish** creates an immutable numbered revision; later draft edits never alter existing assignments or attempts. The test panel can launch the latest published revision as a full shared session for controller/readback testing. Each attempt creates new aircraft identifiers and resets messages, event outcomes and exercise time.

Assignments pin a revision to a mentee's account/Discord user ID, with an optional UTC due date and attempt allowance. Due dates are displayed for scheduling; they do not lock out overdue training. A mentor starts the attempt; the assigned mentee joins or resumes it from My assignments. Other mentee accounts cannot claim that session, even with its link. Ad hoc sessions retain their existing link-based access. Each exercise still has one control seat and one mentee seat.

The authoritative server scheduler advances only on exercise time. Pause freezes events; reload/reconnection preserves their persisted outcomes and does not replay them. Closing all pages stops offline catch-up. Future traffic definitions, event actions and instructor notes remain server-private; mentees receive the public briefing, live traffic and messages. The staff Timeline drawer shows event states and manual controls.

**Restart attempt** archives the current exercise/events, consumes another allowed attempt and restores the pinned revision at 00:00 with its existing seats. Stale/repeated lifecycle requests cannot affect the new attempt. **Finish attempt** freezes the exercise and saves its snapshot, event results and optional mentee feedback. Ending a session archives any active attempt before deleting the live session/link; published revisions, assignments and attempt history remain. Assessment is manual: finishing an event list does not award a pass, and this milestone has no automatic grading, replay viewer or notification delivery.

## Radio audio

Both views include Audio on/off and Voice controls. Playback defaults on; the explicit on/off choice is remembered in browser local storage per account and role. Online permission and voice selection remain per tab. A playback failure does not overwrite the saved choice. Device voices may load after startup; new transmissions wait for them automatically. If the browser blocks autoplay, the next click or key press in the simulator retries the queued transmission without muting audio or requiring an off/on toggle. Both roles hear new Ground and Tower transmissions regardless of the selected frequency. Published ATIS changes automatically queue the full published text. Switching frequencies, new messages and manual replays preserve the current transmission and queue. Repeated snapshots, initial history and reconnection history do not replay old messages or ATIS. Muting, reset, disconnect and leaving the page stop pending speech. A staff Pause suspends speech and retains new pilot requests for playback on resume.

Mentee frequencies count aircraft with an unanswered pilot request on that channel. The frequency selector and strip Commands backgrounds pulse #FFF600 yellow until a substantive controller response. The aircraft icon itself pulses between its normal color and #FFF600 without a flashing background. Opening a log does not clear request attention; Standby retains it. Reduced-motion preferences use steady #FFF600. Readbacks, assignments and Unable replies to commands remain in the log/audio but never add request counts or attention, including restored snapshots from previous versions. Strips show callsign, runway and aircraft type. Staff controls include a global message log across frequencies and an aircraft log for the selected traffic, including its messages on previous frequencies. These read-only logs do not acknowledge requests.

Voice settings provide a device voice selection, speed, volume, Test voice, Replay last message and Stop speaking. The mentee ATIS view can read only the published ATIS. Runway numbers and frequencies use digit-by-digit pronunciation. Voice, rate, volume and online-voice consent stay in the current tab; the account/role’s on/off choice is remembered in this browser.

Speech uses the browser-native [Web Speech API](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis), with automatic preference for a local English voice. Online voices are labeled and use the browser speech provider. There is no application speech API, microphone permission, recording or paid service. Voice availability and sound quality depend on the device/browser. Unsupported browsers keep the simulator usable with audio unavailable; playback failures retain the enabled choice and queued transmissions and show a retry explanation.

## Exercise controls

- Select traffic in the staff list to edit callsign, aircraft type, frequency, runway, altitude, pattern, landing outcome, heading or speed. Spawn airborne/ground traffic, reposition it, or remove it. Reset restores the sample exercise after confirmation.

- Calculate an A* taxi route to Runway 06 or 24 from Routes & position, or assign a mentee Taxi to Runway instruction. Routing follows connected OSM taxiway/stand centerlines, rejects aircraft too far from that network, excludes the runway protected area and stops at a generated hold-short point. It does not invent a straight-line shortcut when the snapshot has no connected route. Manual routes remain available.

- Clear/draw a taxi path by clicking map waypoints. Mark hold-short points with the checkbox before placing them. Taxi stops at each unreleased hold and the route destination; Cross Runway releases the next hold. Taxi routes and displayed flight plans are separate.

- Draw flight plans with map clicks. A selected aircraft displays its plan in the mentee scope; deselection removes that overlay. Plans do not steer traffic.

- Mentee ATC panels queue supported commands for staff response. **Readback** acknowledges without changing movement; **Readback & assign** acknowledges and executes the stored instruction once; **Unable** declines without executing. Assignment revalidates current frequency, aircraft state and routes. Old snapshots without stored instructions remain readable and can be assigned manually through flight controls.

- **Automatic** applies to all aircraft. Every new session, import and scenario launch starts on, regardless of legacy account defaults. Staff can turn it off for that session; reconnecting, Reset and restarting an attempt preserve that explicit session setting. When enabled, the latest pending instruction is acknowledged and assigned after 1.5 exercise seconds. Pause freezes the delay; manual replies and newer commands supersede queued replies, and disabling cancels them. Enabling also queues existing pending instructions. Invalid assignments receive Unable with the reason; manual retunes cancel automatic assignment of the old-frequency command. Replies are logged and spoken without becoming requests. Automatic also drives the intention-based requests described below.

- Pushback approvals with a cardinal tail direction use the same queue/readback flow. Assignment reverses the parked aircraft at up to 3 KT onto the mapped taxiway behind its nose, then turns the tail along that centerline in the requested direction and stops. An aircraft without a reachable mapped taxiway behind it cannot assign pushback; check its stand position and orientation. This is simple training motion, not a model of individual stand pushback procedures.

- Final supported command choices send immediately from the message list, without a second confirmation panel. Invalid choices show their validation reason and remain disabled. Unread pilot messages belong to their original frequency and retain read state across transfers; an open extended panel marks new messages on that frequency read. Both frequency logs include all transmissions, with the other frequency in gray. Off-frequency aircraft symbols remain visible, but their tags appear only while selected.

- The staff view uses one unified radar with Ground and Tower traffic visible together, a traffic roster and a contextual bottom dock. It has no frequency tabs or ATIS editor. Choose Pilot messages, Flight controls, Routes & position or Aircraft details for the selected aircraft. Runway-specific pilot requests include a separate requested-runway selector and preview; sending a request does not change the aircraft’s assigned runway.

- Takeoff clearances can be sent before a pilot request or runway placement. Readback & assign calculates an A* ground route, taxis onto the runway, back-taxis to its threshold, aligns with its centerline, then accelerates to rotation. Departures use the full runway length. Invalid unmapped ground routes still require staff repositioning before assignment. Make Right/Left Traffic sets the departure pattern; option clearances apply their requested hand after the touch-and-go, preserving the current circuit until touchdown.

- Tower Sequencing provides numbers 2–8 and source-defined follow-traffic legs. Option/landing clearances include numbers 1–8; pattern entries support sequencing. Sequence commands resolve the valid preceding aircraft on the same runway. Pattern traffic extends downwind and adjusts base/final speed to follow it; general conflict avoidance remains outside this prototype.

- The selected staff aircraft shows its projected movement in gold, active circuit in blue, and the opposite circuit dotted. Frequency is always available beside the selected callsign. Both roles animate the same kinematics at display frame rate between compact authoritative motion updates; message history is shared only when it changes.

- Unsupported operational choices remain browsable with an explanation and no enabled Send action. Report User, guard warnings and external actions are unavailable. Procedure routes, fixes, airspace and winds aloft are visual demonstrations, not navigational data.

- ATIS edits remain drafts until Publish. Selected ATIS tiles use white borders; unselected borders are gray. Runway text color represents wind independently of selection: green headwind, amber when crosswind dominates, red tailwind. Other tile text remains neutral. Procedure selection previews all overlays only while the menu is open with no selection; selected overlays persist after closing. Opacity affects procedures alone.

The pure engine in `engine.ts` uses fixed simulation steps, gradual turns/speed changes, a continuous five-leg pattern with turn anticipation and runway-centerline final interception, plus simple runway rollout. Ground steering in `ground-movement.ts` anticipates turns without snapping aircraft to corners. Taxi, lineup and pushback traffic slow or stop behind traffic on their upcoming route with a .045 NM (about 83 m) minimum gap, and resume when it clears. Spacing is independent of frequency and roster order, and shares the same rules with display prediction. Controller holds remain explicit. Defaults are centralized in `model.ts` (1,500 ft AGL, 15 KT taxi, 3 NM pattern width). The default circuit establishes final about 4.5 NM from the threshold; its base corner includes the turn radius so aircraft do not finish joining almost a mile closer in. Heading overrides suspend pattern navigation. A runway change preserves position, pattern leg/hand and heading overrides. Crossing and merging routes reserve a deterministic winner until it clears the shared corridor, preventing mutual taxi waits. Same-route queues keep their following gap. Give way assigns a named priority aircraft; opposing traffic uses a mapped alternate when available and otherwise remains separated. Airborne collision avoidance and realistic aircraft performance remain outside this prototype.

Airborne speed targets are IAS: 250 kt Inbound outside/leaving the pattern, 220 kt on upwind/crosswind/downwind (210–230 kt), 180 kt on base (180–200 kt), 180 kt outside 4.5 NM final, 160 kt at or inside 4.5 NM final (140–180 kt), and Vref 135 kt at or inside 2 NM. Takeoff and go-around use the combined upwind/crosswind/downwind phase. The engine ramps at 3 kt/s instead of changing speed instantly. The trainer's Airspeed ribbon and each scenario aircraft's Phase speeds settings accept a fixed positive whole IAS target per phase. Blank fields persist as null and restore that phase's automatic defaults. Fixed phase targets also provide their own sequencing speed floor; other phases remain automatic. Scenario revisions retain the optional `speedTargets` map for initial and scheduled traffic, and each session receives its own copy.

A trainer speed maneuver sets the optional `speedMode` to `manual`, retaining the global requested target across leg changes. Selecting Auto/Semi-auto resumes the configured phase profile without discarding its settings. Editing a phase also resumes the profile. Older snapshots and scenario seeds without these fields use automatic speeds; existing authored speed maneuvers still select manual mode. Ground movement retains taxi/rollout speeds. These are simplified training kinematics: the IAS number also drives map motion without a separate TAS, wind or atmospheric model.

## Verification

The selected aircraft's remaining taxi route appears as a bold green line in the mentor view. Drag a segment to insert a waypoint at release, or drag an existing waypoint to move it; only the active waypoint marker is shown. Edits preserve taxi progress, hold-short flags and automatic tower handover, including queued runway exit routes. Reached hold points cannot be moved away from the stopped aircraft. Route changes during a drag are rejected so an old edit cannot replace a new clearance. Only the current staff seat can edit routes.

Additional Tower controls support line up and wait (both runway ends), cardinal-direction departure approval, runway exits and transitions. Line up and wait uses the departure entry route, aligns at the threshold and remains stopped until a separate takeoff instruction is assigned. Existing saved lineups without the optional wait flag retain their takeoff behavior.

Full-stop arrivals automatically take the first mapped exit reachable after braking: 15 KT for ordinary connectors, 35 KT for forward high-speed connectors. The map has no speed tags, so a connector is treated as high-speed when its departure geometry is within 60° of runway travel; reverse use is ordinary. Selection follows joined taxiway pieces, respects an assigned exit side, and keeps the aircraft on the runway until the connector entry. Unavailable assigned exits produce Unable. Expedite/traffic variants change radio wording only. Touch-and-go traffic continues into takeoff.

With Automatic enabled, once clear (0.06 NM from the runway centerline), a full-stop arrival without an assigned exit command requests frequency change on Tower, then requests parking after Contact Ground. An assigned exit-runway command or Tower Taxi to Parking command retains the exit route, tunes Ground once clear, and requests taxi to parking directly. Turning Automatic off suppresses these generated requests and retunes. Pausing freezes them, save/reload preserves pending work, and rendering predictions never retune or send messages. Ground's Taxi to Parking clearance plans a protected route to a reachable mapped stand, respecting occupied destinations and the staff parking intention.

Transition minimums are offered from 500 to 10,000 feet MSL in 500-foot steps. Assignment leaves the landing circuit, cancels landing clearance and continues on the present heading, climbing to the minimum if needed without descending from a higher altitude. Staff controls the crossing track and the timing of the clearance so the aircraft reaches the minimum before overflying the airport. Departure approval turns airborne traffic onto the selected cardinal heading at its current altitude. These clearances use the existing readback/assignment workflow; all Misc messages are radio-only, have no automatic readback and do not change movement. Contact Other Frequency omits the aircraft's tuned channel.

### Sequencing and radar history

- Staff sees all pending controller messages but may answer only the latest. Readback, Readback & assign or Unable consumes that pending batch; older commands remain in the log and cannot be assigned afterward.
- Sequence commands (including a pattern entry with sequencing) identify the actual preceding aircraft by runway, number and announced leg. A numbered landing clearance does not assign a follow target. Number 1 needs no sequence. Final is shared by left/right patterns.
- Valid arrival sequences steer pattern traffic: downwind extends until the predecessor is on base/final and the predicted arrival leaves at least 45 seconds or 1 NM at the predecessor's speed. The extended base/final geometry persists for the circuit; automatic speed reductions respect the active IAS segment's minimum (never below 135 kt Vref). Manual speed overrides retain the legacy 80 kt spacing floor. Manual extensions and heading overrides take precedence. The follow-aircraft highlight is shown only on the staff scope. This is pattern sequencing, not general conflict avoidance or a guarantee for deliberately unsafe placements/overrides.

## Intentions and Automatic requests (1.8.53)

The staff **Intentions** tab and scenario aircraft setup share flight intention (Pattern work / Departure), Landing outcome (Touch and go / Full stop), Taxi intention (Taxi to runway / Taxi to parking, with optional mapped stand), and airborne After transition (Continue transition / Request touch and go overhead, default radius 1 NM). Landing outcome uses the existing aircraft landing setting. A ready-for-departure request changes taxi intention back to runway. Explicit controller instructions override intentions.

**Automatic** replaces the old readback label. Its circled question mark explains readbacks, requests, handoffs, clearance enforcement, pause behavior and intentions. Pushback completion requests taxi using the latest published ATIS. **Contact Edinburgh Tower when ready** defers the handoff until the actual assigned-runway departure hold, then requests departure, adding remaining in the pattern when intended. These transitions send requests once and require controller clearances before movement proceeds.

Scenario authors can choose **Request Transition at Start**, assign a transition altitude, or configure an **Overhead** condition with a radius. The transition overhead intention requires transition approval and Automatic, and requests inbound for the option once inside that radius. It does not grant pattern entry, sequencing or landing clearance, and adds no arrival shortcut for the mentee.
